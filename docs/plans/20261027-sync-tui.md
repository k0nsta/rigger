# Sync in the TUI

## Overview
- `rigger sync` in a terminal opens a Bubble Tea flow instead of typed prompts (`1-N/i/enter`, `2*`, `none`, `-2`). It is the daily command, and the prompts break down at scale: with 85 strays the list scrolls away and each package is answered blind (release check, 2026-10-26).
- Screens: commit picker → strays → pull → incoming changes → run → summary, in the look of `rigger` / `init`.
- Typed prompts stay for no terminal, `--plain`, and `--yes` keeps answering nothing at all. Scripts, cron and the coming background sync are unchanged.
- Interactive `rigger apply` (no `--yes`) opens the existing TUI at the review screen instead of its y/n confirm.
- Ships as v0.2.0. Replaces `docs/backlog/sync-has-no-tui-screen.md`.

## Context (from discovery)
- `cmd/rigger/sync.go` (553 lines) holds the flow and its prompts together: `sync` (guards: host file, `repo.ReadHead` branch guard) → `exportLayouts` → `handleStrays` (darwin only; `syncer.Strays`, `AddToBrewfile`, `ignore_packages`) → `pickFiles` (`syncer.Changes`) → `sy.Commit` → `sy.Pull` (`ErrConflict` + `conflictFix`, `ErrUncommitted`, `ErrNoAnswer`) → reopen session → `applyFromRepo` (pending = not settled, not offer-only, not needs-secret; `Session.Origin`, `askApply` with prerequisites auto-included, `Session.DropFromHost` + commit of the host file, `decideReplacedLinks`) → `Push`.
- Prompt helpers: `askStray`/`validStrayAnswer`, `parseApplyAnswer`, `askChoice`, `printTargets` (Brewfile label + profiles via `Manifest.ProfilesOf`), `printEvent`. Tests: `cmd/rigger/sync_test.go`, `tests/e2e_test.go` (sync round trip, feature-branch refusal).
- `internal/tui`: one `Model` with screens `scrHost … scrError`; `Planner`/`Applier`/`Store` consumer interfaces in `dependency.go` + mocks; the run screen consumes `engine.Event`s; sudo passwords reach the TUI as `PasswordRequest` over a channel (`AskFunc`), the pattern this plan reuses for questions from the flow.
- `cmd/rigger/tui.go` `interactive` builds `tui.Config` (Warning from `ReadHead`, Passwords, LogDir) and runs the program; `cmd/rigger/apply.go` `confirm` is the y/n prompt.
- `rigger remote` runs the TUI over `ssh -t`, so sync there has a terminal too.
- TUI tests drive the model with `pump`/`press`/`view` in `internal/tui/tui_test.go` over a real session with a fake brew on PATH.

## Solution Overview
- **One flow, two front ends.** The sequence moves out of `cmd/rigger/sync.go` into `internal/syncflow` (`Run(ctx, deps, asker, report)`). Every question goes through an `Asker` interface; progress goes through a `Reporter`. The prompt front end is today's code behind `Asker`; the TUI front end answers the same calls.
- **Questions over a channel.** The flow runs in a goroutine; each `Asker` call sends a request with a reply channel to the Bubble Tea program, which shows the screen for it and replies on enter: the same shape as `PasswordRequest`. The flow stays sequential and testable; the TUI stays a view.
- **Separate model.** `tui.Sync` is its own model (not more screens on the installer's `Model`), sharing styles, the run view and the finish view.

## Technical Details

### Asker and Reporter
```go
type Asker interface {
    PickCommit(changes []syncer.Change) ([]string, error)                 // paths to commit
    DecideStrays(strays []syncer.Stray, targets []Target) ([]StrayAnswer, error)
    PickIncoming(items []Incoming) (apply, drop []string, error)          // component ids
    DecideReplaced(links []ReplacedLink) (map[string]LinkChoice, error)   // adopt | keep | leave
}
type Reporter interface {
    Step(name string)            // export, strays, commit, pull, apply, push
    Line(text string)
    Event(ev engine.Event)
}
```
- `Target` = Brewfile path, label (`dev`), profiles that use it, and whether this host has it; plus the "ignore here" and "later" targets.
- `Incoming` = component status, reason (`Session.Origin`), prerequisites that come with it.
- `ErrQuit` from an asker: stop before anything is written (strays not saved, nothing committed).

### Screens
- **Commit**: checklist of changed files, all ticked; `space` toggle, `a`/`n` all/none, `enter` on a row toggles a diff preview (`git diff -- <path>`, first 30 lines), `c` continue.
- **Strays**: one row per package: name, description, target. `←`/`→` cycle the row's target (each Brewfile with its profiles, ignore here, later); `A` applies the current row's target to every row; `/` filters by name; `tab` switches formulae/casks; scrolls with the cursor; summary line "12 to dev, 3 ignored, 70 later"; `c` continue.
- **Pull**: spinner; on conflict, uncommitted changes or no answer, the error screen shows today's message and the commands to run.
- **Incoming**: checklist of pending components with state and reason; `d` marks "drop from this host" (✗, needs a confirm line naming `hosts/<host>.yaml`); a prerequisite of a ticked item is ticked and locked with "needed by …"; replaced links get a decision row (adopt / keep repo / leave) as in the installer's review.
- **Run and summary**: the installer's run view; then push and a summary (committed N, added N to Brewfiles, ignored N, applied N, dropped N, pushed).

### Front-end choice
- `sync`: TUI when stdin is a terminal and neither `--yes` nor `--plain`; prompts when there is no terminal or with `--plain`; `--yes` as today.
- `apply` without `--yes` in a terminal: the installer TUI opens on the review screen with the saved selection (`--profile`/`--only` honoured).

## Decisions
- Flow and front ends are split so background sync can reuse `syncflow.Run` with an asker that answers "later" to everything.
- Strays answered "later" are not stored; they come back on the next sync, as today.
